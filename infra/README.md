# Fleet Governance: local Agora stack

Docker Compose stack that runs a fleet's governance read side (DAO Node,
CPLS, Agora Next) against a real Anvil chain, plus one command that deploys
a fresh fleet and drives one proposal through it end to end. See
`../docs/spec.md` for the product spec and `../docs/compatibility-notes.md`
for every integration quirk found while building this, with commands and
outputs.

## One command

```bash
bash infra/scripts/bootstrap-local.sh
```

From an empty Anvil, this deploys a five-member fleet, configures DAO Node
and Agora Next with the real addresses and ABIs, brings up the read side,
and drives one scripted proposal (open task, propose, five reasoned votes,
queue, execute) through the real governor with `cast`, syncing CPLS's
archive after each safe stage. It prints the proposal's Agora Next URL when
done. Safe to re-run against an already-running stack (Compose recreates
only what changed); **not** idempotent against contracts already deployed
on the same Anvil, by design (it always deploys a fresh fleet, per the
spec's own end-to-end lifecycle). Start from a genuinely empty stack with:

```bash
cd infra
docker compose down -v            # add -f docker-compose.offline.yml too if you used it
bash scripts/bootstrap-local.sh
```

`down -v` is required (not just `down`) whenever a Postgres stub table
changes, since Compose only runs `postgres/init/*.sql` against a fresh
volume.

Each of the five scripts under `scripts/` can also be run on its own; see
each script's header comment.

## Ports (host access)

| Service | Port | Notes |
| --- | --- | --- |
| Anvil | 8545 | `cast`, `forge script --rpc-url` |
| Postgres | 55432 | not 5432, so this stack can run alongside a host Postgres; container itself still listens on 5432 |
| DAO Node | 8000 | `/v1/progress`, `/v1/proposals`, `/v1/proposal/<id>`, `/v1/vote_record/<id>`, `/v1/delegates`, `/v1/balance/<addr>` |
| CPLS | 8001 | `/health`, `POST /jobs`, `GET /jobs/<id>` |
| fake GCS (offline only) | 4443 | `GET /storage/v1/b/<bucket>/o` lists archive objects |
| Agora Next | 3000 | `/proposals`, `/proposals/<id>`, `/delegates` |
| blockcache-shim | (internal only) | see below |

## Services

- **anvil**: local chain, `--block-time 2`, chain id 31337.
- **postgres**: `agora_web2`, `agora_web3`, `runner` databases; `agora_web3`
  carries every stub table Agora Next (and, for `fleet.votes`, CPLS) reads,
  generated by `infra/postgres/gen-stub.ts` from `vendor/agora-next`'s own
  Prisma schema, plus a handful of hand-written raw-SQL tables neither
  Agora Next's Prisma schema nor any upstream model declares (see that
  file's `FLEET_RAW_SQL_TABLES`/`SNAPSHOT_RAW_SQL_TABLES`/
  `AUAZURE_RAW_SQL_TABLES`).
- **dao-node**: indexes the fleet's chain events in memory; needs
  `infra/dao-node/abis/<lowercase address>.json` for the token and the
  governor at boot (written by `write-daonode-config.sh`) plus
  `TOKEN_ADDRESS`/`GOVERNOR_ADDRESS`/`DAO_NODE_START_BLOCK` in `infra/.env`.
  `NUM_ARCHIVE_CLIENTS=1` is also required (see
  `infra/dao-node/patches/` and `docs/compatibility-notes.md`): left at
  upstream's default of 2, the realtime client that tracks new votes,
  queues and executions never starts at all, silently, with no error.
  `infra/dao-node/patches/0005`-`0007` fix three more gaps found running
  a real proposal through this deployment for the first time (an empty
  `/v1/proposal_types` list with no onchain type registry, a missing
  `voting_module_name` for a plain `propose()` call, and
  `to_dict()` never actually using its own `start_block`/`end_block`
  properties); see each patch's header comment.
- **blockcache-shim**: a minimal local stand-in for the real, hosted
  "blockcache" service CPLS's DAO-node sync calls for block timestamps and
  a few other per-chain lookups; backed by this stack's own Anvil. See
  `infra/blockcache-shim/server.py`'s header comment and
  `docs/compatibility-notes.md`.
- **cpls**: reads DAO Node, writes gzipped NDJSON proposal and vote
  archives to a GCS bucket. Its vote source for a DAO-node-tracked proposal
  is a Postgres table (`fleet.votes`), not DAO Node's API; in production a
  separate indexing pipeline this local stack does not have populates it,
  so `scripts/scripted-proposal.sh` inserts one row per real on-chain vote
  itself. See `docs/compatibility-notes.md`.
- **agora-next**: the fleet governance UI, reading balances/delegates/
  proposal types live from DAO Node, and proposals/votes/vote-history from
  CPLS's archive (`use-archive-for-*` toggles in
  `infra/agora-next/overlay/src/lib/tenant/configs/ui/fleet.ts`).
  `infra/agora-next/patches/0002` routes every server-side archive read
  through `node:http`/`node:https` instead of the global `fetch()`: this
  Next.js version's patched `fetch()` reliably threw
  `TypeError: controller[kState].transformAlgorithm is not a function`
  reading a gzip response body server-side, which every call site already
  caught and silently treated as "no data", so pages rendered 200 OK
  with an empty proposals list and no visible error. The proposal vote
  list itself (with reasons) is a client component
  (`ArchiveProposalVotesList`, `"use client"`) fetching
  `/api/archive/votes/<id>` after hydration: it will not appear in a
  plain `curl` of `/proposals/<id>`'s initial HTML even though the data
  is correct (verified directly against that API route, the same one the
  browser calls after hydration); see `docs/compatibility-notes.md`.

## Where the archive lives

CPLS writes to the GCS bucket named by `GCS_BUCKET_NAME` (default
`fleet-archive-dev`), under `data/fleet/...` (proposal listings, per-
proposal detail, `votes/<proposal id>.ndjson.gz`) and `jobs/<type>/...`
(one record per job run). Locally (no `GCS_CREDENTIALS_FILE` set) this is
the `fake-gcs` container from `docker-compose.offline.yml`, browsable at
`http://localhost:4443/storage/v1/b/fleet-archive-dev/o`; create it with
`bash infra/scripts/create-fake-bucket.sh` (idempotent; `bootstrap-local.sh`
already calls it when running offline).

### Reproducing the archive from empty

```bash
cd infra
# delete every object in the bucket
curl -s "http://localhost:4443/storage/v1/b/fleet-archive-dev/o" | jq -r '.items[].name' \
  | while read -r name; do curl -s -X DELETE "http://localhost:4443/storage/v1/b/fleet-archive-dev/o/$(python3 -c "import urllib.parse,sys; print(urllib.parse.quote(sys.argv[1], safe=''))" "$name")"; done
# re-trigger a sync (same payload shape scripted-proposal.sh posts; see its
# trigger_cpls_job function) and re-check
curl -s -X POST localhost:8001/jobs -H 'content-type: application/json' -d @/tmp/sync-job.json
curl -s "http://localhost:4443/storage/v1/b/fleet-archive-dev/o" | jq -r '.items[].name'
```

## Switching to a real GCS bucket

Set `GCS_CREDENTIALS_FILE` in `infra/.env` to a real service-account JSON
key path, and bring the stack up with the base file only (no
`docker-compose.offline.yml`):

```bash
cd infra
docker compose down -v
# Build every image once, before anything is started, and never pass
# --build to `compose up` again afterwards. Every service shares one build
# context, so `up --build <subset>` re-evaluates the build for the whole
# dependency graph; even a 100% cache hit produces a new image ID, which
# makes Compose recreate the already-running anvil container to match it and
# wipe the chain the fleet was just deployed to (anvil has no volume). This
# is the sequence bootstrap-local.sh uses, for that reason. See
# ../docs/compatibility-notes.md, Task 6, "docker compose up --build
# recreates Anvil out from under a deployed fleet".
docker compose build anvil dao-node cpls agora-next blockcache-shim
docker compose up -d anvil postgres
# ...deploy + write-*-config.sh as bootstrap-local.sh does...
docker compose up -d dao-node cpls agora-next blockcache-shim
```

`cpls`'s `GOOGLE_APPLICATION_CREDENTIALS` and `agora-next`'s
`ARCHIVE_GCS_BUCKET_OVERRIDE` both already point at a real
`storage.googleapis.com/<GCS_BUCKET_NAME>` URL in the base compose file;
only the offline overlay repoints them at `fake-gcs`. `bootstrap-local.sh`
itself detects this the same way: it only layers
`docker-compose.offline.yml` and creates the fake bucket when
`GCS_CREDENTIALS_FILE` is unset.

## Pointing at Base Sepolia instead of local Anvil

This stack's own contracts deploy is Anvil-only (`FLEET_DEPLOY_CONFIG=
../deployments/configs/local-5.json` uses Anvil's default accounts). To
point the read side at a fleet already deployed on Base Sepolia:

1. Deploy there directly with `contracts/script/DeployFleet.s.sol` (see
   `contracts/README.md`), pointed at a Base Sepolia RPC URL and a real
   deployer key, with `FLEET_MANIFEST_OUT` set to this worktree's
   `deployments/31337/latest.json` (the filename is chain-id-named on
   `main`, but every script here reads that fixed local path; rename the
   directory to match if you want to keep multiple chains' manifests side
   by side, and adjust the scripts accordingly).
2. Set `CHAIN_ID=84532` (Base Sepolia) in `infra/.env`.
3. Run `write-daonode-config.sh` and `write-agora-next-deployment.sh`
   (unchanged; they only read the manifest and `CHAIN_ID`/
   `CONTRACT_DEPLOYMENT` from `infra/.env`).
4. Point `DAO_NODE_ARCHIVE_NODE_HTTP`/`DAO_NODE_REALTIME_NODE_WS` (in
   `docker-compose.yml`'s `dao-node` service) and `NEXT_PUBLIC_FORK_NODE_URL`
   (`agora-next` service) at a real Base Sepolia RPC/WS URL instead of
   `http://anvil:8545`/`ws://anvil:8545`.
5. `infra/blockcache-shim` only proxies to `ANVIL_RPC_URL`; either repoint
   that env var at the same Base Sepolia RPC URL too, or (simpler, and
   correct for a real chain CPLS's upstream config already might know
   about) unset `BLOCKCACHE_URL` on `cpls` so it falls back to the real
   hosted blockcache service.
6. `scripts/scripted-proposal.sh` uses Anvil's well-known default account
   keys; driving a real Base Sepolia proposal needs real funded keys
   instead, passed the same way (`--private-key`), and the fixed sleeps
   (voting delay/period, timelock) replaced with whatever that
   deployment's real parameters are.
